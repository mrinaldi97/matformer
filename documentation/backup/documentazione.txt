#MatformerTask
[[dataclass:TaskConfig | Dataclass]] [[file:matformer/tasks/task.py | Code]]
Tasks are a very important concept in the MatformerArchitecture. In general, they mean "do something with a model", wheter it means perform an evaluation, generate text, run interpretability plugins or even just run a forward pass on the model. While training is currently not routed through the MatformerTask, in theory even the training process could potentially be reframed as a particular kind of task. What matters is that MatformerTask provides a unified interface to run "something" on the model, providing an abstract class and a specific interface for the experimenter to add a very large variety of tasks.
The concept of a "task" revolves around three things: data, model and loggin/reporting.
[[file:matformer/tasks/task.py | MatformerTask:__init__]]'s init initialize the [[MatformerDataloader]] dataloader, very similar to how the [[MatformerTrainer]] works; a specific dataset can be used for a task using a data section in the [[MatformerConfigs]] YAML file where its name correspond to the "ref_data" field in the [[dataclass:TaskConfig]]. A task, however, is not forced to have a dataset loaded, as they are used also for the interactive mode, where the task is executed batch by batch in an interactive manner. MatformerTask can either use the model defined in the [[dataclass:MatformerModel | model's config section]] or a [[VirtualModel]], where activations from a model were previously collected. 
After, the init initialize a [[MatformerSaver]], a simple class that saves the possible output from a task (ex. results of an annotation, or the final evaluation's log); in the near future, it is possible that Saver and Logger will be unified and abstracted together.
When the task begins, by simple [[file:matformer/tasks/task.py:__call__ | calling]] the task's instance, it call the begin_task() function, which tasks can subclass to execute single instruction before the task's loop begin. Then, each batch is wrapped between optionals "batch_pre/post processors", useful for more complex evaluation scenarios (noop as default).
Each specific task must implement a "process_batch" function. This function must return the batch itself (to be used for eventual postprocessors) and an optional dictionary (None if this is not relevant for this task) that can be then handled by the saver (for example to save the result coming from each single batch). [[file:matformer/tasks/task.py:save_batch | save_batch]] is indeed called after each [[file:matformer/tasks/task.py:wrap_process_batch | processed batch]].
Because many tasks can benefit from accumulating states batch-by-batch to compute results at the end, when all the data is passed through process_batch, [[file:matformer/tasks/task.py:compute_summary | compute_summary]] is called, which, by internally calling the task's optional function "compute()", allow the task to perform a final compute and return an optional "summary" dictionary, that will be saved by the [[MatformerSaver]] in a separate section/file. An optional end_task() function is called before returning the optional summary or None to the caller.
Tasks can be explored through the Registry: [[registry_category:tasks]]
Some bult-in tasks are "generation", which autoregressively generate texts for GPT-like models, "evaluation", which by mimicking the same process used during training (the use of [[LearningSignals]]), is perfect to perform general evaluation (for example, accuracy, perplexity, f1...) as well as perform forward passes of classification models. "forward" is a dummy task, but very useful: it just perform a forward pass on the model, but this can be very useful if [[Plugins]] are attached to the model; a perfect use case for this dummy forward pass is to capture activations for a [[VirtualModel]].
Writing a task is very easy, and it is a very flexible way to do any kind of thing with a model loaded with Matformer, such as benchmarking or perform interpretability studies. For this reason, you can follow the [[tutorials:add_a_task | tutorial to add a task]].

#MatformerConfigs
Matformer contains a complex configuration system that is able to control in an integrated manner all the framework's components. 
Classes that requires a configuration must have their dataclass. This dataclass is automatically discovered by the [[MatformerRegistry]] with the decorator @register_dataclass. 
The MatformerConfigs class is then able to load YAML/JSON config file(s) into a tree of typed MatformerConfig dataclasses.
Because dataclasses are very flexible and able to configure almost every aspect of the framework, you can use the special [[dataclass]] section to explore all the configuration's options for anything registered in the [[MatformerRegistry]]
For example, let's assume the YAML contains
    data:
      - name: train
        type: HFDataset
      - name: test
        type: HFDataset
this means that the MatformerConfigs will look in the registtry for a dataclass for the category "data" and of variant "HFDataset", which is addressed by the special "type" key. If the "type" key is missing, MatformerConfigs will use category's default (default=True in the registry).
Another special, optional, key is "name" as it is specialized for giving a unique alias to a specific object in the Configs system: this is necessary when the objects present in the configuration compose with each other, for example when a specific evaluation task refers to a specific dataset on which the task is evaluated.
When a MatformerConfigs is created or updated, it is possible to provide several files (ex. a list of YAMLs). In this case, the order may be important: if a section is declared more than once, its existing fields are patched from left to right, the latest imported file wins. Files may also include other files by declaring a special section "includes". Includes are the first element resolved, so they are lowest priority. Highest priority are "overrides", which can be set at any moment and give the user a final decision over the MatformerConfigs object.
An important distinction is that some categories only allow for a single configuration object; for example, it is possible to have only a single "model" section and so if more than one "model" section is present, their content get merged as explained above. Some categories, however, may allow for more than one configured object, as it is the case for the "data" and "task" sections. They are distinguished because their dataclass inherit from "MatformerMultiConfig" instead of "MatformerConfig". When it is initialized, MatformerConfigs automatically checks if there are inconsistencies (clearly, all the variants of a category must either be all grouped or all listed). 
It is particularly for "MultiConfigs" dataclasses that the "name" field exists, in order to avoid ambiguities. In this way, it is possible to have named object in the configuration tree, and those objects can refer to each other. This behaviour is governed by the dataclass itself.thanks to three ClassVar:
    _ref_fields: ClassVar[dict] = {"ref_section": "section_name"} 
        _ref_fields in this case is saying to MatformerConfigs that the configuration's key "ref_section" must contain the reference to an object registered in the section "section_name". For example,     _ref_fields: ClassVar[dict] = {"ref_data": "data"} means that the configuration of this object should contain a field called "ref_data" containing the name of a (named) object insterted in the "data" section.
        If this is the data section:
            data:
              - name: train
                type: HFDataset
              - name: test
                type: HFDataset
        this means that this config should contain a "ref_data" key with either "train" or "test" as a value. 
        The referenced object is automatically looked for by the MatformerConfigs systems. If it missing, no errors are raised if the key doesn't appear in the _mandatory_references: ClassVar[list] = [] classvar; in the counter case, an exception is raised. After the object is looked for, it is automatically linked: this means that calling my_section.ref_data will resolve to data.train.
        my_section:
            my_value: 1
            foo_value: bar
            ref_data: train
        Because this "linking" capability can be useful in some cases, the "linked_fields" classvar acts a syntactic sugar to directly have a specific section linked inside the configuration object. 
A MatformerConfig object can also be used to rapidly instantiate the configured object. For example, if we have loaded a tokenizer's configuration:
    tokenizer:
        type: huggingface
        pretrained_name: mrinaldi/Gettone
we can get an instance of the actual tokenizer with configs.tokenizer.instantiate() [matformer_configs.py #instantiate]


# Learning signal & Learning signal selector
## Learning signals
Because Matformer should support even experimental settings, the [[MatformerWrapper]] doesn't hard-wire any specific learning signal. Model being trained for autoregressive objective, classification, masked language model, flow matching has no direct impact on how the training step is written in the wrapper: this stays generic and the actual signal used is provided by the registry. Moreover, being Matformer a framework designed with experimentation in mind, there is the possibility to have more than one learning signal in the training run: the correct learning signal could be chosen stochastically, or data-wise or even more than one learning signal can be mixed together.
Each LearningSignal is based on the abstract class [[py_file:matformer/matformer/training/learning_signals/learning_signals.py | LearningSignals]] whose methods are executed on a specific order by the wrapper.
1. prepare_inputs receives the batch and return a tuple, (input_sequence, metadata). The wrapper will then make a forward pass to the model passing the returned input_sequence to it. The model is eventually run with the kwargs specified in the learning signal's model_kwargs dict. 
2. select_targets receives predictions - the raw model's output -, the original batch and the metadata object. It returns (predictions, targets), already flattened and ready for the loss function.
3. The wrapper then use the loss function defined in learning signal's loss_function and sum this loss to the total loss of the batch, ready for the optimizer
4. As a final, optional, step an hook on the learning signal is called, post_loss, which passes (loss, predictions, targets) for other things, such as additional logging.
An easy good example of a learning signal, that can be used as a basis if you need to write a new one, is [[py_file:matformer/matformer/training/learning_signals/masked.py | Masked]], used for bert-like models.
Learning signals are indexed by the registry in the category [[registry_category:learning_signals | learning_signals]]. Click to explore them!
## Learning signals selector
The most common case is that the learning signal selector acts as a no op and just a single learning signal (ex. autoregressive) is use for the training. However, Matformer adds an extra layer of flexibility by allowing to:
- Switch learning signal automatically depending on data or stochastically
- Mix learning signals together
To understand how to write a Learning signal selector, is again useful to refer to the [[MatformerWrapper]] which handles all the dialogue with the LearningSignal selector in the training step.
0. The selector is initialized in the wrapper's init, and the selector is populated with all the configured learning signals, by directly accessing the [[MatformerConfigs]] object. 
1. ls' pre_step is called with the raw batch, an optional hook for anything not foreseen
2. The wrapper sends (batch, batch_idx) to the ls' "pick" function. The Learning Signal Selector will return to the wrapper the list of LearningSignals active for this step; the wrapper will iterate on them executing the pipeline already explained in the [[LearningSignals]] section. If for a specific batch more than one learning signal is returned, their losses are summed.
Matformer provides by default "single" (the no-op for a single ls),"multitask" (to sum several ls together) and a stochastic selector. Other selectors can be explored through the registry: [[registry_category:learning_signal_selector | learning_signal_selector]]. The stochastic selector is a good starting point to write a custom selector.

# MatformerWrapper
    The ModelWrapper contains methods to load checkpoints, weights as well as everything required to train the model.
    The training procedure itself, however, is not hard-coded into the Wrapper but is handled through another class,
    called LearningSignal. The LearningSignal is the one containing the actual preparation of the inputs 
    (ex. masking for Bert-like models) and the selection of targets for the loss function.
    For more complex scenario, it is possible to use a "LearningSignalSelector", another class that select the correct LearningSignal according
    to specific criteria step by step (ex. to randomly mix more LearningSignal(s) or to correctly route the data according
    to info present in the batch's metadata.)
    The LearningSignal, LearningSignalSelector and the model class are all accessed through the [[MatformerRegistry]]
    
    MatformerModelWrapper is one of the most important components of the architecture: any MatformerModel must be wrapped inside the ModelWrapper to enable frameworks' functionalities. MatformerModelWrapper inherits from [[MatformerModule]] and [[PluginManager]], which means that [[Plugins]], a fundamental feature of Matformer, are managed by the Wrapper.
    Any model executed or trained by matformer is initialized inside the wrapper, and its reference is stored as self.model.
    The Wrapper is also responsible for the handling of [[VirtualModels]], that is, models that are not executed live but whose activations are rather retrieved from an activation store, which is a useful feature for interpretability, distillation or model's debugging. To understand VirtualModels, the activation store and how the wrapper is able to switch from "live" to "virtual" runtime_mode, please see the [[VirtualModels]] section.
    In the __init__, after having initialized plugins and the eventual virtualmodel, the model is created and the [[MatformerTokenizer | tokenizer]] attached. If the wrapper is initialized in training mode (the [[MatformerConfigs]] contains a "training" section]], the [[LearningSignal]] is initialized, and models' weight are [[py_file:matformer/utils/initialization.py]] initialized and, if necessary, some of them may be frozen according to the "freeze" config (see: [[freezing | Freezing]])
    Because any forward pass to a Matformer model will pass from the MatformerModelWrapper makes sure that any tensor passed to the forward will be wrapped in a [[TensorDC]] before getting inside the model. Thanks to this, matformer's neural network modules don't have to worry about the tensor being a TensorDC or not: plain torch.Tensor will never pass the barrier of the MatformerModelWrapper's forward.
    The MatformerModelWrapper is responsible for the inner part of the training step, the one called by the [[MatformerTrainer]].
    ## Training step
    1. Check if the batch's [[TensorDC]] has the special attribute "worker_has_finished" set to True. In this case, loss is immediately set to 0.0; this is necessary when ranks get out of sync during distributed training, for example when a GPUs exhaust the training data while other GPUs are still busy.
    2. LearningSignalSelector is asked for the list of active learning signals, and they are used to compute the loss. Check [[LearningSignals]] for detail!
    3. Loss is logged
    4. The wrapper now will scan the dictionary "aux_losses" contained in the [[MatfomerCache]]. If any additional loss is present there (ex. a Moe router loss), it is added to the loss and logged separetely.
    5. Learning rate is logged
    6. Total loss is returned.
    The whole training step is guarded by a try except block. If an Exception is found, particularly if this step got OOM, the current batch is skipped and gradients cleared. It is a dirty workaround, but it may be helpful to avoid a catasthrophic training run loss if just few batch errors out. Clearly, it must be thought as a workaround that breaks training correctness: it is duty of the user to decide how many failed training steps can be tolerated.
    
    ## Model loading
    The wrapper is also the entry point for loading models, either for inference or for finetuning / inheriting of weights.
    The loading system is very flexible and will be explained in two steps, here and in the [[CheckpointHolder]] documentation page.
    the [[file:matformer/matformer_wrapper.py:load_model | load_model function]] builds a model from scratch and returns it to the caller.
    This function can create a model in different ways:
    - If you provide just a [[MatformerConfigs]] object, it creates a fresh model ready for training
    - If you provide a path OR a [[CheckpointHolder]], the config and models are loaded from the checkpoint (with the term 'checkpoints' we intend also published weights, such as HuggingFace repositories);
    - If you provide BOTH (path/checkpointholder) + configs, what happens is that the config is at first initialized from the path and then overriden with the fields provided with the configs argument. This is particularly useful to train derived models, for example a classification fine-tuning starting from a pre-trained language model. The sections that are inherited from the base checkpoint can be chosen with the "inherit_section" argument
	After the weights are loaded or initialized, the wrapper checks for the presence of the "weights" section in the [[MatformerConfigs]]; if this section is set, it allows to load full or partial weights from arbitrary many other models. This is helpful for experimental settings, as it allows to perform model stiching. 


#TensorsDC
As you will see by browsing the code, plain torch.Tensor(s) are rarely used inside Matformer.
Instead, all tensors are wrapped inside a custom dataclass, whose base is called TensorDC.
The reason why TensorDC are uses inside Matfomer is twofold:



1) Handling of padding/unpadding
a PaddedTensor is a datastructure where a tensor with batch dimension (B,S) is supplied with a boolean padding mask. 
The padding mask should have FALSE for each position that contains true data and TRUE for any padding position.
Having defined a PaddedTensor gives several advantage. First of all, you will not have to worry again about the padding mask: this will be embedded into the
tensors' dataclass. Then, you will have access to the .unpad() method.
The .unpad() method of PaddedTensor objects convert the PaddedTensor into an UnpaddedTensor. Unpadded tensor [...]
Other useful methods available in the PaddedTensor objects are .detach(), which returns a list of tensors each of its "true" length, without any padding, 
and .pad_right() which converts the padding convention from [...] to [...] in order to be used for scenario such as autoregressive generation.

2) Carrying of additional data.
The TensorDC objects can carry with themselves additional data apart from the tensor itself and its padding mask.
For example, so
Sometimes those extra tensors should follow the main tensor during the padding/unpadding operations. In those cases, the tensors should be added as
"following_attributes". A typical example is the "cloze_mask" used by masked models and used in the training step to recall if at that position there 
was a normal token or a [MASK]. The cloze_mask should be of the same shape of the original tensor, thus it will be included in the "following_attributes".
On the contrary, an example for an attribute that should NOT follow the main tensor in its pad/unpad tour is the "same_doc_mask" tensor. This tensor
is generated by the default Matformer dataloaders to signal if the current chunk belongs to the same document of the previous batch (more info [[here|same_doc_mask]]). 
In this case, it will enter inside the attributes.
While the following_attributes must be torch.Tensor of a compatible shape with the main tensor, the attributes are completely free.
They can be tensors, such as the "same_doc_mask", but even other types. For example, a convention in Matformer is to keep the ["metadata"] key of 
the attributes dict free to store metadata of the documents contained in the batch. While it may seem weird to carry metadata (such as author,
genre, year and so on) inside the TensorDC, it proved to be an handy solution for experimental scenario such as when an hook connected deep inside the model
(ex. for interpretability purpose) should access the metadata to store them in an external database together with the models' intermediate activations.

!TLDR: To run a plain-tensor nn.Module over a TensorDC, keeping the wrapper and all its attributes, use the sugar x.apply(module).

# MatformerTrainer
The single entry point for anything related to models' training is the MatformerTrainer class. Its role is to correctly set up the training procedure, including handling distributed training, iterating through the batches of data performing the training steps, launch evaluations or generic tasks whenever certain conditions are met and finally save the trained models. 
Its init is divided in eight steps, that we will briefly enumerate; more details can be understood by directly looking at the code. 
1. "_setup_fabric()" => Currently, Matformer is hardcoded to rely on torch fabric, which is a good choice to simplify the code regarding distributed training and mixed precision strategies. In th future, this function could became an optional step. Its scope it's very simple: it sets up the parallelism strategy (currently hardcoded to "ddp", see the [[Limitations]] page and, if training runs on more than one rank, distributed the work on all the requested accelerator.
2. _setup_checkpoint() => This function works with [[CheckpointDirectoryManager]] class to understand if the present training run should be started from scratch or resume (either from the latest trained step or for a specific step/version specified by the user). If a checkpoint is resumed, a [[CheckpointHolder]] (of native matformer type) is created; if the training starts from a pre-trained model, a [[CheckpointHolder]] of the correct type is created (for example, an huggingface's checkpoint holder to fine-tune a model coming from HF); it returns None if the training starts/restarts from scratch.
3. _setup_model() => Creates or load the model using the [[MatformerModelWrapper]]. NOTE: this steps expands the original MatformerConfigs object with the configuration of the loaded model: this allows, for example, to have a ClassificationModel agnostic to stuff such as hidden_size or layer number, because those fields depend on the base model loaded and are populated in this step, inside the [[MatformerModelWrapper]]. After, missing/unexpected keys, both from the base model/checkpoint as well as from the [[AdditionalWeights]], is reported. Finally, model is eventually compiled respecting the [[config:TrainingDataclasses]] configuration.
4. _setup_data() => here a [[MatformerDataModule]] is instantiated, and the total number of training steps, batches and token per batch is computed (see [[file:matformer/training/matformer_trainer.py:count_training_steps()]]
5. setup_optimization() => [[this.optimizers | Optimizers]] and [[this.lr_schedulers]] are configured;
6. _restore_states() => If training is resuming from a checkpoint, states of optimisers, lr_scheduler, datamodule, step and epoch are restored from the [[CheckpointHolder]] 
7. _setup_logger()
8. _setup_fabric_wrapping()

After the trainer is initialized, run() launch the training, which is handled by the train() function, which wraps the trainig loop and, if requested, saves model and/or pugins in the checkpoint's folder at the training's end. 

## The training loop
Before starting the training loop, validation groups are normalised so that, if they are set in the config with a fraction of total steps, the config is overridden with their actual value according to the total training steps.
After this, the training starts, optionally controlled by [[Control]] which allow for dynamically stop the training or perform an arbitrary [[MatformerTask | task]] during the training, useful for scenarios like booked Slurm clusters or to do model's diagnosis without interrupting the training. The actual loop proceeds through all the epochs and steps, performs evaluations (actually, any [[MatformerTasks]]) at the requested step/epochs and save intermediate checkpoints. It exposes useful generic hooks:
- self.model.on_epoch_start at each epoch start 
- currently other hooks are comented out

# MatformerRegistry
"""
    =The Matformer Registry: customization of modules =
    The Matformer architecture tries to avoid every direct instantiation of hard-coded classes of neural network components.
    Instead, every implementation of the core components is managed by the MatformerRegistry. This means that it is possible
    to define modules for every component of the model, such as MLP, attention implementations, layer normalizations...
    In this way the model is not bound to specific implementation (such as vanilla pyTorch) but it is immediately possible
    to adopt different kernels without touching a single line of the core transformer implementation
    This gives extreme flexibility to the developer: just by putting python files in the repo's folders (or specific additional folders) and decorating 
    the class with a decorator it is possible to substitute every module of the network as well as add new components to the framework, such as new [[MatformerTask | tasks]].
    By using the registry it is also possible to import customized experimental modules that can be hooked to many different entry points of
    the model, and, if necessary, they can be trained together with the rest of the network!
    Adding custom components to a transformer model has never been so easy.
    
    The registry has the following hierarchy:
        _registry (dict)
            category (dict) <= example "attention","norm","linear","embedding","mlp","loss"
            variant (dict) <= example "geglu","swiglu","rmsnorm","flash","gated_deltanet","mamba"...
            name (dict) <= example "torch","liger","nvidia-transformer-engine"... this is the name of the actual implementation
                name contains: 
                    * requires => List of required libraries, useful for auto-fallback if not supported
                    * priority => The priority of different variants, ex torch 0, liger 1, nvidia 2 and so on
                    * constraints => Constraints (ex. ["is_training"]) this implementation is compatible with;
                                    see the "Constraints" section below
                    * metadata => Free dictionary of metadata
                    * params_names => A mapping that renames the parameters to create universal checkpoints compatible also
                                        with different implementations
     
     == Add a custom implementation ==
			Put your script in repo's folders, or, to keep it out of the repo, in
			MATFORMER_ASSETS/extra_plugins (see [[env_vars:MATFORMER_ASSETS]]): the registry
			scans both.
            Then, you don't have to do anything by hand, as the registration is handled by an easy to use decorator, example:
            from matformer.matformer_registry import registry
            @registry.register("mlp", "swiglu", "a_name_for_your_swiglu_kernel",
                   params_names={'w13.weight': 'gate_proj.weight', 
                                  'w2.weight': 'down_proj.weight'}, priority=100,requires=["torch","my_custom_library"])
            class MySwigluImplementation(nn.Module):
				(your code here)
				@staticmethod
				def _test():
					# Return True (or simply don't raise) if this kernel really works on this machine
				
			
			
            It's very simple to define a module and let Matformer handle the picking of correct implementation for you:
            registry.create("mlp", "swiglu", hidden_size=768, ffn_factor=4)
    These are the only requirements to seamless integrate different custom implementation of basic modules into a Matformer model! Just be careful to 
    match conventions for param_names if you want that your model correctly loads also with other implementation.
    
    == Adding custom modules to the model  ==
    
    The registry can also be used to add hooked modules/functions to any part of the model.
    The main transformer block exposes the following entry points:
			* pre_attn
			* pre_mlp
			* post_mlp
			* pre_output
	Let's say you want to add a custom module before the mlp. What you need to do is just to insert into the "external modules" directory a file
	my_module.py
		from matformer.matformer_registry import registry
		@register.registry("hook","name_of_my_hook","default")
		class ACustomModule(nn.Module):
			(your code...)
	
	Then, in the model config's JSON file the hook should be attached in this way:
		    "default_layer": { (or custom layer)
					[other params...]
				  "hooks": {"pre_mlp":"name_of_my_hook"}
				},
	If the modules contains trainable parameters, it will be trained togheter with the model.
	That's it! 

    == Preferences, availability tests and constraints ==

    Implementation choice can be steered without touching code: the environment variable
    MATFORMER_<CATEGORY>_<VARIANT> (ex. MATFORMER_ATTENTION_NORMAL=sdpa) forces a specific
    implementation, and create(..., preferred='liger') does the same programmatically. Otherwise the
    priority queue decides. Once an implementation is chosen it is instantiated; if it cannot be
    built, the registry simply tries the next one.

    Availability tests: an implementation may define a class-level `_test()` static method, a few
    lines that really exercise the kernel (import it and run the smallest possible call). It is run
    by the registry at instantiation time - never during the AST discovery, which stays completely
    lazy - and its outcome is stored globally, so a whole model pays the cost only once and a
    failing kernel (ex. flash-attn installed but useless on a CPU-only machine, or compiled for
    another CUDA version) is skipped forever after without repeating the test. Any raised exception
    or a False return means "don't use me here".

    Constraints describe what an implementation can be used for, ex. an hypothetical FlashInfer
    kernel usable for inference but not for training:

        @registry.register("attention", "normal", "flashinfer", priority=20, constraints=["is_inference"])

    registry.create("attention", "normal", constraints=["is_training"], ...) then skips it, even if it
    has the highest priority; the same happens with registry.set_default_constraints(["is_training"]),
    which activates a constraint for every subsequent create() call. An implementation that declares
    no constraints is considered universal and is never filtered out; a kernel can also declare the
    constraints it does NOT support, ex. constraints={'is_training': False}, in which case everything
    else stays compatible.

    == requires, constraints, metadata: three different things ==

    They are easy to mix up, so the rule of thumb is:
        * requires     -> external LIBRARIES the implementation needs to exist at all
                         (ex. ['flash_attn']); unimportable => the implementation is not a candidate.
        * constraints  -> whether the implementation MAY BE SELECTED in the current context
                         (ex. is_training, softcap); not satisfied => skip it and take the next one.
        * metadata     -> how to CALL an implementation that has already been selected (tensor order,
                         packed-qkv support...); it is attached to the instance as _matformer_metadata
                         and it never influences the choice.
    A capability whose absence forces a fallback (ex. flash-attn not doing tanh softcapping) is a
    constraint, not a metadata: declaring it as metadata would leave the caller to discover, at
    forward time, that the chosen kernel cannot do the job.

    == Errors ==

    Every error raised by the registry is a RegistryError subclass: ImplementationNotAvailable
    (missing dependency or failed _test), ImplementationInitError (the constructor of the chosen
    implementation raised; the original traceback is preserved, so it points at the user's module and
    not at the registry) and NoImplementationAvailable (every candidate failed: the message lists the
    reason of each attempt). A failing implementation never silently ends the search and never
    returns an object that isn't the requested module.

    There is exactly one registry per process. matformer/matformer_registry.py builds it once at import time; every
    `from matformer.matformer_registry import registry` elsewhere in the codebase (or in your own modules) gets that
    same instance, already populated. Never call MatformerRegistry() directly.

    == Linking config dataclasses ==

    A dataclass can be bound to a registered implementation with register_dataclass, instead of carrying its own
    bookkeeping fields:

        @registry.register("saver", "JSONLSaver", "default")
        class JSONLSaver: ...

        @registry.register_dataclass("saver", "JSONLSaver", default=True)
        @dataclass
        class JSONLSaverConfig(SaverConfig):
            filename: str = "output.jsonl"

    Every YAML section is keyed by category and picks its variant with a "type" field
    (saver: {type: JSONLSaver, ...}); a section with no "type" falls back to whichever
    variant was registered with default=True. load_config.instantiate() then resolves a config
    straight through the registry, so the config dataclass itself carries no bookkeeping fields
    and no build() logic.

#The neural network: transformer blocks, sockets, residual stream

Matformer is primarily designed to train and execute Transformer models. However, its structure potentially allow for the introduction of different architectures too, provided they follow the coding style required to cleanly integrate into the architecture.
Models should be registered in the "model" category of the [[MatformerRegistry]] using as class decorator @register.registry("model","model_name") and they should subclass [[MatformerModule]]. For the development of transformer models, however, it is possible to use the classes already available for this family of models.
Matformer's transformer model implementation tries to be the most abstract and compatible possible. Indeed, at the current state, it is already able to correctly define all the most important families of common open weights LLMs and this abstract design pattern allow the experimenter to have a great flexibility in defining transformer models. (see [[dataclass:models_dataclasses]]) If this flexibility is not enough, it is always possible to expand the definition of the models by writing [[Plugins]] or, if even this is not enough, neural modules can be added into the registry and new models registered in the "model" category.
Transformer's implementations lives in the "transformer_blocks" [[file:matformer/transformer_blocks/ | folder]] and, in particular, in the files "[[file://matformer/transformer_blocks/transformer.py | transformer.py"]], which defines the core transformer blocks, and [[file://matformer/transformer_blocks/heads.py | heads.py"]] containing input and output heads required for language modelling. Multimodal support is in development. Full models, which subclass the core components contained in transformer.py and head.py, can be found in the "transformer_blocks/model" folder, and are directly explorable using the [[registry:models]] registry documentation helper. 

## NakedTransformer
[[file://matformer/transformer_blocks/transformer.py:NakedTransformer | NakedTransformer ]] defines a transformer backbone without input and output heads. With the default configuration settings, it works like any standard transformer implementation: it instantiate a list of [[file://matformer/transformer_blocks/transformer.py:TransformerBlock | TransformerBlock ]] and passes the output of each block to the input of the next one. However, it contains useful features such a flexible "layer_schedule", which gives the native support for looped models, and the possibility of asking directly to the forward to have the signal to entry at a specific transformer block and exit before the full list is iterated. The, optional, final norm, with or without bias, is configurable.
The NakedTransformer defaults to a standard [[registry:stream.residual_stream | additive residual stream]] but this is configurable too (see the [[SocketPluginsStream | Socket, Plugins & Stream ]] section). The NakedTransformer exposes the following sockets:
* layer_{i} => by default, mounted with the i-esim TransformerBlock 
* final_norm => if configured, mounted to the final normalisation, Identity if empty
* before_unembed => an optional, defaulting to Identity, socket useful for interpretability or extra functionalities. Executed after the final_norm.

## TransformerBlock
Each TransformerBlock can be configured with a [[registry:norm_style | normalisation style]] so that it can support pre-norm, post-norm, sandwich norm and personalized normalization position. It creates a stream with an [[registry:mlp | MLP]], for example a SwiGLU block, a [[registry:sequence_mixer | sequence_mixer]], such as a [[Attention | self-attention]] block, and, for each normalisation slot configured in the normalisation style implementation, a [[registry:normalization | normalisation]] block (ex. RMSNorm).
The forward pass executes [[SocketPluginsStream | sockets ]] in this order:

#SocketPluginsStream
In Matformer, any neural network can be defined with having one or more "Socket" where components ("Plugins") are "mounted" and integrated in the computational graph. This is particularly handy for several reasons: it allows for being very [[Intro:design_pattern | DRY]] when extending the implementation to support very different model families, it permit to insert extra components into the computational graph natively, as if they were hard-coded into the architecture, without having to resort to pytorch's hooks, and allow for inspection and intervention at any stage of the computation, which is a very useful feature for Interpretability experimentation. Finally, the Socket/Plugin system allows for the easy replacement of any components, for development or experimental purposes.
While this system may seem confusign at a first glance, it is actually very simple.
Each [[MatformerModule]], for example the [[file://matformer/transformer_blocks/transformer.py:NakedTransformer | default modules of transformer models]] inherit from [[file://matformer/plugins/socket_mixin.py:SocketMixin | SocketMixin]] and, at initialization time, should call "init_sockets" with a specific stream type (default to residual stream, but potentially could be AttnRes, mHC or whatever else). Any useful position in the network's computational graph should be added as a socket, for example "attention" or "normalization" or "mlp". Adding sockets is inexpensive, because if unpopulated they default to identity. For this reason, it is suggested to add sockets to any position that can be useful not only for default components to sit, but also where inspection or additional plugins could be mounted, wheter in training or during inference. [[file://matformer/plugins/socket_mixin.py:Socket | Socket]], indeed, contain inside an ordered list of components, which can be empty, that can be reordered, inspected and where components can be easily removed, inserted or replaced.
